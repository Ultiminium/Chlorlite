## Fixed / implemented this pass (previously declared-but-unimplemented — link errors)

- **Material setters**: `cc_material_set_base_color/roughness/metallic` — were
  declared in render.h with no implementation. Now live (renderer + engine wrappers).
- **ECS query shorthands**: `cc_query1/2/3` — implemented with order-preserving
  trampolines (cc_query_run sorts types internally; the shorthands remap comps[]
  back to the caller's argument order). Verified: query2 matches exactly the
  entities having ALL listed components, correct component data.
- **`cc_texture_from_memory`**: decode PNG/JPG/etc from an in-memory buffer
  (stbi_load_from_memory).
- **`cc_draw_mesh_wireframe`**: real GL_LINE polygon-mode draw of a mesh's edges
  in a flat color, composited into the gbuffer.
- **`cc_draw_bounds`**: transform-space box outline via the gizmo line system.
- **`cc_mesh_load_obj`**: Wavefront OBJ importer (v/vt/vn/f, polygon fan
  triangulation, a/b/c + a//c + a face formats, negative indices, normal
  recompute when absent). The master-list "asset importer (OBJ)".
- **Immediate-mode GUI toolkit** (`cc_gui_*`): window, label, button, slider,
  checkbox, separator — the master-list "immediate-mode UI toolkit." Renders via
  the 2D overlay (cc_draw_rect/cc_draw_text), interacts via cc_mouse_pos/down,
  captured in screenshots. New file engine/src/gui.c.
- **`cc_draw_text_wrap`**: word-wrapped multi-line text.

## EXTENSIBILITY AUDIT — open mechanisms vs closed "type" enums (this session)

PRINCIPLE (from user, now a standing rule): this is a game ENGINE, not Scratch.
Systems must expose MECHANISMS a developer extends with their OWN behavior — NOT a
fixed enum of engine-blessed "types" to pick from. Built-ins are fine only as
OPTIONAL PREWIRED EXAMPLES of the same open path. Applied to interactables, then
swept across every system. Audit of all 26 public-header enums:

  OPENED THIS SESSION (were closed behavior-menus, now extensible):
   - interact.h CCInteractType -> cc_interactable_create + CCInteractDesc callbacks
     (on_interact/focus/unfocus/update + your state). Built-ins = examples.
   - camera.h CCCamControllerType -> cc_cam_use_custom(rig, fn, state): your
     controller runs every cc_camera_update; you own the motion. free/orbit/
     follow/path = examples. (CC_CAM_CTRL_CUSTOM added.)

  ALREADY OPEN (escape hatch exists — not a trap):
   - render.h CCShadingModel is a closed set of BUILT-IN shading models, BUT the
     engine already exposes arbitrary GLSL: cc_shader_load/_load_src/_load_spirv,
     cc_post_custom (custom fullscreen passes), cc_shader_set_* uniforms. A dev can
     write any material/post shader. Left as-is (built-ins are conveniences).
   - anim state machine, physics injectable body, scripting (C/Rust/Python), event
     bus (open channels >= CC_EVT_USER), ECS (register any component/system), tween,
     coroutine (any step fn) — all already callback/registration-driven.

  LEGITIMATELY CLOSED (engine/hardware facts, NOT behavior menus — correct as enums):
   - CCLightType, CCPixelFmt, CCRendererBackend, CCMeshUsage, CCShapeType,
     CCBodyType, CCWaveform, CCGamepadButton/Axis, CCLogLevel, CCCvarType, CCCamEase,
     CCCameraType (persp/ortho), CCBillboardMode, CCDebugView, CCCoroCmdKind,
     CCConditionOp, CCInputSource, CCMChunkType/InterpType/TrackTarget,
     CCDirectorPhase (the director's own FSM; a dev writes a different director).
     These describe what the hardware/renderer/format physically supports.

RESULT: no closed enum forces a developer into an engine-blessed set of game
behaviors. Every game-logic extension point is a mechanism (callback + your state)
with built-ins as optional examples. CARRY THIS FORWARD for any new system: expose
the mechanism first, ship built-ins as examples second.

## Honest bottom line

The engine is a genuinely capable, ~14k-line real-time renderer + ECS + asset
pipeline. The *engine-primitives* clusters (rendering, geometry, animation,
architecture) are largely complete. The *game-content & gameplay* clusters (world
interactables, save/load, dialogue, AI director, audio mic input) are the large
remaining surface — these are the horror-game concept's critical path and each is
a substantial feature in its own right, not a quick wire-up. This pass closed
every *declared-but-unimplemented* API gap that was tractable (GUI, material
setters, OBJ import, ECS queries, wireframe/bounds, texture-from-memory, text
wrap) so the public header surface no longer lies about what's callable; the
remaining gaps are documented above with honest effort estimates.
